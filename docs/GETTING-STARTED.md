# 项目理解与复现指南

本项目在正点原子P5（XCZU4EV）学习板上完成Linux实时内核部署、系统测量，以及Linux与A53 Core3最小通信验证。它为后续两轴驱控业务接入提供实验基础；现有控制环、电机与产品核心板尚未纳入验收。

只关心结果，请直接阅读[完整成果报告](reports/PROJECT-REPORT.md)；遇到故障，查[问题与处理记录](TROUBLESHOOTING.md)。本指南说明先理解什么、准备什么、按什么顺序复现。

## 1. 先理解运行结构

一个Linux实例使用A53 CPU0—2；独立Core3运行最小通信程序。AMP（Asymmetric Multiprocessing，非对称多处理）在这里指：A53 CPU0—2共同运行一个Linux系统，由Linux统一调度；Core3不归这个Linux系统调度，而是独立运行最小通信程序，即裸机。

Linux侧的测试程序通过设备节点`/dev/p5-core3`访问Linux通信模块，由通信模块把消息写入专用共享内存；独立运行的Core3程序读取消息并处理，再通过共享内存返回应答，最后由Linux通信模块将应答交给测试程序。完整路径为：Linux测试程序 → `/dev/p5-core3` → Linux通信模块 → 专用共享内存 → Core3程序；应答经反向路径返回。这里的设备节点是用户态测试程序访问内核通信模块的入口，共享内存则是Linux侧与Core3之间实际交换消息的区域。

双方采用轮询方式检查共享内存，即主动、反复查看是否有待处理的消息或应答，而不是等待对方通过中断通知。两个传输方向各有一个消息槽，分别用于Linux向Core3发送消息和Core3向Linux发送消息；它们不是可连续存放多条消息的队列，发送与接收需要按协议协调消息槽的使用。

消息中包含会话、序号、epoch和CRC等字段。会话用于区分不同的通信会话，序号用于标识会话中的消息并核对应答；epoch是服务重置时更新的通信状态版本标识，用于区分重置前后的通信状态，避免把旧状态下的消息当作当前消息处理。CRC（Cyclic Redundancy Check，循环冗余校验）用于检查消息数据是否发生损坏。这些字段共同支持消息识别、应答匹配、数据校验及服务重置后的状态区分；其中，通信服务状态重置不等于Core3硬件复位。

当前实现是基于专用共享内存和轮询的最小通信方案，未采用RPMsg（Remote Processor Messaging，处理器间消息框架），也未使用通知中断。

私有内存为`[0x60000000,0x60200000)`，共享区为`[0x60200000,0x60400000)`；两区均在设备树（Device Tree，描述硬件与资源配置的数据）中预留并设置`no-map`。正常启动Linux三核并不自动证明Core3已启动。

| 版本／场景 | 用途 | 新成员最容易混淆的区别 |
| --- | --- | --- |
| baseline／原始RT | 对照启动、实时内核部署与唤醒短测 | 原始RT包没有通信实验的内存预留 |
| 诊断内核 | ftrace事件跟踪与性能硬件计数 | 配置、跟踪开销与原始RT不同，不直接比较最大值 |
| r001基础包＋r004临时载荷 | 已验证的最终最小通信组合 | r001是第1次修订的基础启动包；r004是第4次修订的通信模块及Core3程序，需每次手动加载 |

这里的“r001基础包＋r004临时载荷”是两部分配合运行：r001放在SD卡上，上电后启动Linux，并为Core3及共享内存预留空间；r004包括Linux通信模块和Core3程序，在Linux启动后手动加载到RAM，再核对状态并单次启动Core3。r004没有写进SD启动包，因此断电后r001仍在，r004会丢失，下次上电需要重新加载。顺序是：**SD卡启动r001 → 手动加载r004 → 核对状态并启动Core3 → 运行双向通信测试**。

r002是第2次修订的心跳程序，r003是第3次修订的消息程序；它们保留用于解释历史，不是首次复现应选的最终版本。G0—G5中的G为Gate，表示六个验证关卡。

## 2. 复现前取得的材料

| 条件 | 要求／来源 |
| --- | --- |
| 仓库与下载权限 | 克隆本项目组仓库，并能访问其Release附件 |
| 实板 | P5 XCZU4EV、匹配载板／硬件设计、电源、SD与读卡器；软件目录中的P5B名称不代表其他板型自动适用 |
| 操作连接 | 串口115200、8N1、无流控；同一串口只由一个程序占用。文件传输方式须能核对大小和摘要 |
| 仅重放已验证镜像 | 从下节对应Release下载，核对外部SHA-256（文件内容摘要）和包内校验清单 |
| 从源码重建 | 原ALIENTEK-MP工程、Xilinx 2020.2工具链／sysroot、原rootfs和匹配硬件输入；仓库并未包含这些全部输入 |

原执行主机为Ubuntu18.04，AArch64 GCC9.2.0。只克隆仓库不足以从零生成相同启动文件；源码重建说明尚未在另一台全新主机完整重放。缺少原工程输入时，应先取得输入或选择已验证Release，不能以任意版本替代后宣称复现一致。

## 3. 选择一条复现路线

### A. 复现原始RT部署与内核测试

1. 按[部署指南](DEPLOY.md)从[原始启动Release](https://github.com/maxwell-motion-measurement-rd/p5b-linux-rt/releases/tag/board-boot-20261027)下载，备份原SD文件，先核对baseline，再部署RT。按指南核验版本、`realtime=1`、CPU集合`0-2`与模块目录。
2. 如需从源码生成，先执行[源码重建说明](build/REPRODUCE.md)。固定厂商父提交和RT提交，重建匹配模块与FIT（Flattened Image Tree，多载荷启动镜像）；不要重复应用两种等价补丁入口。
3. 按[内核测试方法](reports/rt-assessment-summary-20261029.md)选择原始RT的cyclictest短测，或从[诊断 Release](https://github.com/maxwell-motion-measurement-rd/p5b-linux-rt/releases/tag/diagnostic-ftrace-20261029)下载已验证镜像，按[诊断部署指南](DIAGNOSTIC-DEPLOY.md)做ftrace／perf；需要修改配置时再单独构建诊断内核。保存当轮命令、配置、直方图、退出码和内核日志。
4. 预期是能够重复测量与保存证据，不要求恰好再次出现1255µs或1293µs。没有复现尖峰不等于问题修复；工具退出码为0也不等于产品实时合格。

### B. 复现Linux与Core3通信

1. 下载[通信手动快照Release](https://github.com/maxwell-motion-measurement-rd/p5b-linux-rt/releases/tag/amp-comm-validation-20261030)的`p5-amp-manual-r004-20261030.zip`和校验文件。解压后，先使用`sd-base-r001/`中的基础启动文件部署SD卡并启动Linux；再将同一ZIP的`ram-r004/`中的`p5-core3-comm.bin`、`p5_core3_comm.ko`、`g5_test`和`g5_snapshot`传到板端Linux的`/tmp/amp-r004/`目录，按[板端手动启动](build/AMP-REPRODUCE.md#板端手动启动)一节校验摘要、加载驱动、检查状态并单次启动Core3。文件传输完成不代表已加载或已启动Core3。不要拿原始RT的`image.ub`替换通信基础镜像。
2. 严格按[通信构建与手动加载指南](build/AMP-REPRODUCE.md)核对预留区、Linux CPU0—2、载荷摘要与模块版本。构建r004时使用`amp/core3-g4/`和`amp/linux-g4/`，测试工具在`amp/linux-g5/`。
3. 冷启动后加载模块，但不自动唤醒Core3；检查`attempted=0 pm_query=0 pm_state=0`后仅请求启动一次。预期状态页版本4、`core=3 el=12 state=1 reason=0`、异常字段为0且心跳增长；`el=12`是寄存器编码，不是“EL12”。
4. 先运行指南中的正向、反向、交叉各100次短测。预期各`passed=100 errors=0 missed_release=0`；全新启动每方向计数由0增加到503，已有计数则比较增量。
5. 需要重放完整验收时，先读[G3消息正确性](reports/amp-g3-validation-20261030.md)、[G4故障恢复](reports/amp-g4-validation-20261030.md)和[G5长测及冷启动](reports/amp-g5-validation-20261030.md)。故障测试须在启动前启用专用参数，不能在已接入业务的实例上直接运行。

启动尝试后不热卸载模块、不重试唤醒、不强制复位Core3。异常时先保存状态，按指南同步和卸载存储、正常关机，再整板冷启动恢复。r004断电丢失；自动启动目前暂缓。通信服务状态重置不等于硬件复位。

### C. 不连接板子，核对已有结果

先准备独立的仓库副本，再按[通信指南的离线核对部分](build/AMP-REPRODUCE.md#离线核对已有证据)执行分析器；部分分析器会更新结构化结果文件，不在唯一的原证据目录中重跑。查看[图集](reports/test-results-visualization-20261031.md)及其制图脚本核对内核直方图与54万笔通信延迟。离线核对验证的是保存的数据，不是一次新的板端复测。

## 4. 怎么判断本次复现完成

| 路线 | 至少保留的输出 | 停止条件 |
| --- | --- | --- |
| 内核部署／测量 | 启动身份、CPU与配置、输入摘要、测量参数、直方图／trace及完整性、退出码 | 版本或模块不匹配、工具尚未进入测量、跟踪被覆盖时停止相应结论 |
| 通信短测／完整验收 | 基础包与载荷身份、启动前状态、启动后心跳、模式输出与前后计数、日志 | 内存预留不符、Core3启动失败、无法解释的错误或超时，不继续后续关卡 |
| 离线核验 | 输入摘要、分析器输出、来源与缺口 | 摘要不一致、样本不完整、统计不一致，不用汇总数字替代原始证据 |

每次新复测使用独立结果目录，记录实际日期、镜像／源码／工具身份、条件及结论。原始日志和历史报告保留当期语境；新的结果不覆盖旧证据，也不因后续通过而将先前失败改写为成功。
