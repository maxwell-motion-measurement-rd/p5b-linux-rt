## 建议的下一步：先形成可评审的 RT 工程准入证据

用户已确认：首轮交付源码风险清单、可追溯的RT测试结果和继续／修复／升级建议；同事4.9材料缺失不阻塞当前组合评估。首轮板端对象为P5上独立运行的三核Linux，Core3不启动裸机、不带电机。目标是回答“现有RT组合是否有证据继续承担既定Linux职责”。没有实际业务T／D和允许抖动时，只做风险筛查与性能基线，不能写成产品实时合格。具体负载、测量参数和时长待确认，没有执行。

### A. 固定比较对象并审查源码

1. 固定源码、补丁、配置、DTB、固件、bitstream、rootfs、外部模块、工具链和镜像摘要，保存当前可启动包作为回退。
2. 本地RT输入与上游补丁的字节比较已完成，见前述来源核对；继续核实meta-retis省去ARM32文件段的原因。来源可追溯、补丁内容一致和运行兼容是不同检查。
3. 核对上游5.4.0→5.4.3的修复、RT补丁依赖，以及厂商代码已有的回移和改动。逐项标明已包含、等价实现、缺失、待分析；避免重复套用 stable 修复。
4. 对 RT 修改覆盖的调度、时钟／定时器、锁、中断、ARM64 适配及项目实际依赖驱动做针对性检查。
5. 将已有 baseline 故障与本次 RT 新增异常分开，优先分析影响项目必需接口或 RT 时序的问题。

### B. 补齐测量能力，先测不调优

1. 核对当前板端工具。缺失时准备匹配 ARM64 用户空间的 cyclictest、负载工具、taskset、chrt。
2. 固定当前RT组合的CPU数量、固件、DTB、频率／休眠条件、IRQ、rootfs、模块来源和采样参数，分别记录空载与各负载场景。保留已有回退包，不新增非RT对照镜像。后续比较RT修复版或5.4.3 RT候选时，再使用同一测试矩阵并列明不可避免的版本／配置差异。
3. 先运行空载唤醒测量，再分别施加 CPU、内存、项目必需网络／存储负载，最后在真实可用接口上叠加组合负载。DMA 和 EtherCAT 不存在或未工作时标为未覆盖，不以 CPU stress 代替。
4. 固定周期、测量线程优先级、CPU、采样时长、预热、直方图范围，保存样本数、分布、观测最大值、超期／溢出计数和原始日志。测试时长和通过阈值由后续讨论确定，本文不编造。
5. 关注 panic、Oops、锁／中断异常、失去进展、超期、温度及资源漂移。发生异常时保留触发负载和峰值附近信息，不只记录最后一行最大延迟。
6. 定位峰值时可另准备ftrace／锁诊断用RT镜像。诊断配置会改变开销，其结果与原始RT镜像分开标注；RT场景之间复测保持相同跟踪状态。保留维护核与终端可恢复性，不先照抄优先级99或关闭RT限额。用户已通过Q6接受先测原配置、发现问题后单因素定位的方式。

[Linux 5.4 CPU 参数说明](https://www.kernel.org/doc/html/v5.4/admin-guide/kernel-parameters.html)描述 isolcpus 的范围，默认 domain 隔离主要针对调度域，不代表 IRQ／workqueue 等全部干扰消失；[RT 带宽说明](https://www.kernel.org/doc/html/v5.4/scheduler/sched-rt-group.html)解释运行预算。[cyclictest 测试设计](https://wiki.linuxfoundation.org/realtime/documentation/howto/tools/cyclictest/test-design)强调测量需要与实际负载相关，工具本身不能替代业务任务验收。

### C. 让测试覆盖项目实际 Linux 职责

若沿用现有 AMP 分工，Linux 应测的是指令处理和交付能力，而不是把裸机速度环的抖动直接当作 cyclictest 的通过线。

建议的最小链路是：指令输入 → Linux 解析／规划 → 有界缓冲 → 对端接收／确认 → 状态返回。第一阶段可用清楚标注的对端模拟器；真实 Core3 未运行前，不把它称为 AMP 已打通。

在实际通信方案和对端就绪后，验证命令序号、轴ID、顺序、缓冲区所有权、缓存／内存可见性、通知、过期／重复／丢失检测、超时与停止策略。跨核／跨时钟测量先定义可比较的时钟和测量点。

任务时序应分别记录预定释放时刻 r、开始执行时刻 s、完成时刻 f：唤醒／调度延迟为 s-r，执行时间为 f-s，响应时间为 f-r，截止时间违约按 f > r+D 统计。Linux→裸机接收、真正生效与闭环跟踪另设测量点，不能用一个 round-trip 数字包办全部指标。

### D. 升级候选的条件与后续动作

用户已接受Q4的问题判定原则：明确的必要修复缺失、可重现的内核错误或必需接口的RT新增故障应阻止直接进入下一阶段；单次延迟峰值偏大先定位与复测，不自动决定升级。具体修复／升级分支应根据源码与复现证据评审；后续若确认实际Linux业务要求不能满足，也要分析原因。所有候选均须采用PREEMPT_RT。

“升级到5.4.3”应指纳入相应代码与修复并重新适配厂商支持，不能只修改 Makefile 的版本字符串。候选需重新验证启动链、ARM64、PMU／固件、设备树、板级驱动、外部模块、AMP 约束与同一测试矩阵，不把原有 BSP 支持自然延伸到上游5.4.3。

同事4.9方案应按完整组合比较：准确4.9.x、RT补丁版本／来源、BSP提交、工具与固件、板型、任务、配置、测试条件和原始结果。目前已读资料未提供这些内容。它可能是完整4.9内核路线，不能简化成把4.9补丁贴到5.4。
