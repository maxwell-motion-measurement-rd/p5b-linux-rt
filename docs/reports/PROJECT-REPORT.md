# P5 Linux实时部署与核间通信：完整成果报告

报告日期：2026-10-31。结果覆盖2026-10-27至2026-10-30已归档的部署、内核测量和通信实验，10月31日完成图表与文档整理。本报告汇总当前已完成范围，不表示整个两轴驱控产品已经完成。

## 1. 项目目标与最终结论

本项目在正点原子P5（XCZU4EV）学习板上建立Linux实时运行与Linux／裸机通信的可验证基础，为后续两轴驱控接入提供源码、启动包、复现方法和测试证据。目标分工为Linux负责运动学指令解析、执行与下发，Core3负责后续控制业务；本轮实际运行的是独立最小通信程序，未接入现有控制环。

已完成三个方面：基于厂商Linux5.4.0移植PREEMPT_RT并验证三核启动；完成内核唤醒短测、事件跟踪与性能计数；完成Linux CPU0—2与A53 Core3的最小双向通信、故障恢复、三种条件各30分钟长测和5次冷启动。**通信实验通过，内核负载尖峰原因仍未定位；产品硬实时、实际控制环和电机闭环未验收。**

## 2. 实际实现

Linux作为一个SMP实例使用A53 CPU0—2，Core3运行独立程序；采用AMP（Asymmetric Multiprocessing，非对称多处理）分工。Linux测试应用通过`/dev/p5-core3`和小型模块访问专用共享内存，双方轮询，每方向一个消息槽。

Core3私有区为`[0x60000000,0x60200000)`，共享区为`[0x60200000,0x60400000)`，设备树（Device Tree，描述硬件和资源配置的数据）预留并设置`no-map`。共享区采用Normal-NC（Normal Non-cacheable，普通非缓存）和Inner-shareable（内部共享域属性）映射。Core3不初始化共享中断控制器、串口或DMA，不执行共享L2的全局缓存维护。

消息头40字节，载荷最多256字节；序号、确认、会话、epoch（服务重置时更新的通信状态版本标识）与CRC（Cyclic Redundancy Check，循环冗余校验）用于检查所有权、旧消息与损坏。实验目标100Hz，事务超时100ms、心跳目标每100ms更新、1秒未变化判失联、恢复握手观察窗口2秒。这些是实验配置，不是产品时限。

最终通信环境由两部分配合运行：**r001基础启动包保存在SD卡上，r004通信载荷在Linux启动后手动加载到RAM。** r001是第1次修订的基础启动包，负责启动Linux，并为Core3程序和共享内存预留空间；r004是第4次修订的Linux通信模块和Core3程序，没有写进SD启动包。模块加载后不自动启动Core3，检查关断状态后经PMU（Platform Management Unit，平台管理单元）请求单次唤醒。完整顺序为：**SD卡启动r001 → 手动加载r004 → 核对状态并启动Core3 → 运行双向通信测试**。启动尝试后不热卸载模块、不自动重试或强制复位。断电后SD卡上的r001仍在，RAM中的r004会丢失，下次上电需重新加载；自动启动暂缓。

厂商父提交固定为`62ea514294a0c9a80455e51f1f4de36e66e8c546`，RT提交为`e4cc2d02d270570055fe2b46ca2eb17c21938504`；工具链为Xilinx2020.2 AArch64 GCC9.2.0。补丁名含5.4.3-rt1，源码仍为5.4.0，不能当作完整稳定版本升级。

## 3. 内核测试结果

cyclictest测量周期线程相对预定唤醒时间晚了多少：绑定CPU1，FIFO优先级80，1ms周期。原始RT未为降低延迟修改CPU隔离、IRQ亲和性或PM QoS。空载600秒，其余各60秒，平均／分位数与稀有最大值分别展示。

![内核唤醒延迟统计，空载600秒，其余各60秒](figures/test-results-20261031/01-kernel-latency.png)

| 条件 | 样本数 | 平均µs | P99µs | 最大µs | 严格超过1000µs的样本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 空载冒烟 | 600000 | 46 | 48 | 364 | 0 |
| CPU负载 | 59999 | 46 | 48 | 1255 | 1 |
| 内存负载 | 59998 | 58 | 70 | 1293 | 2 |
| CPU复测 | 60000 | 46 | 47 | 641 | 0 |

P99（99th Percentile，第99百分位数）约表示99%的样本不超过该值。四组直方图无溢出、测量与负载退出码为0；CPU首测和内存组仍有超过1ms的样本。时长不同，最大值不能作为严格场景排名；复测未复现尖峰也不能证明修复。

诊断内核另启用ftrace与A53 PMU（Performance Monitoring Unit，性能监测单元）。首次4MiB／核缓冲覆盖，改为16MiB／核后10秒空载完整复测，得到220415条事件，覆盖／丢弃计数为0。

![完整诊断跟踪的事件计数与局部调度间隔](figures/test-results-20261031/05-diagnostic-trace.png)

30001对目标线程的唤醒事件到调入间隔，平均约3.28µs、最大5µs；同期cyclictest完整唤醒最大86µs。事件对并非测量周期数，局部路径间隔不替代完整唤醒延迟。诊断为空载、不同内核配置，未同步复现原始RT的负载尖峰，不能用86µs宣称改善。

perf软件统计可用；CPU整数循环采到986个软件事件样本，工具报告丢失0，热点通过匹配二进制反汇编定位。诊断版约10秒CPU整数负载记录11943565134个周期、7956337962条退役指令，IPC约0.67；未采匹配访问或分支总数，不计算缓存命中率或分支失败率。这些只描述测试负载，不代表真实控制算法耗时。

证据与口径：[内核测量完整报告](rt-assessment-summary-20261029.md)、[原始直方图汇总](../../logs/rt-risk/2026-10-29/103809-tools/measurements.json)、[诊断事件分析](../../logs/rt-diagnostics/2026-10-29/board-trace/trace-analysis.json)。

正常长测新增通信错误和missed_release均为0，逐笔数据与板端摘要独立核对一致。反向测试由Linux指令触发，不是裸机自主周期业务推送；反向和交叉完整事务都包含两步交互。最大观测耗时4.024ms，不能作为已证明的最坏上界；通信事务耗时与内核唤醒延迟的测量对象不同。

10次客户端重启和10次通信服务重置后，各恢复100笔回显；服务状态重置不复位硬件Core3。5次冷启动各执行三模式各100笔，合计1500笔，无新增通信错误。冷启动验证的是人工上传与单次启动流程。第5次缺少FSBL（First Stage Boot Loader，第一阶段启动程序）／U-Boot（Universal Boot Loader，系统引导程序）早期日志，保留Linux部分日志、用户物理断电确认与通信结果，不补造缺失记录。

故障注入会产生预期超时和拒收，不能概括为所有阶段错误为0；有限样本没有观察到错误也不表示失效率必定为0。

## 5. 问题处理与剩余风险

已修复或绕过并验证的问题包括：Core3频率信息寄存器漏初始化、rt-tests NUMA初始化失败、原内核缺少跟踪／硬件计数能力、跟踪缓冲覆盖及串口数据导出截断。处理分别是频率传递与读回、匹配工具构建、独立诊断内核、扩大缓冲重新采集、分块及整包摘要核对。

仍未定位原始RT负载唤醒尖峰；futex／JBD2修复差异需核对厂商等价实现、系列依赖与触发条件，未证明它们是尖峰根因。原有外设提示、完整兼容性、网络／专用存储压力、长时间联合负载仍需按对应场景验收。详见[问题与处理记录](../TROUBLESHOOTING.md)。
